# cockpit rules

cockpit is a **run hub** that lets any repository whose services start with compose produce a sealed E2E run of one commit and receive the verdict, observations and report bundle in the same shape. The hub (`cmd/cockpit`) owns the sealed compose environment and the run state, and the runner (`cmd/cockpit-runner`) runs TypeScript flows with goja inside the sealed network. Project knowledge comes in with the consumer repository's commit, as scripts, compose overlays and a project declaration (`.cockpit/project.yaml`).

This file holds the rules that every AI coding agent and every person working in this repository follows. The text of the run rules (sealing, lifecycle, verdict) is in `docs/`.

## Vocabulary

- **run**: The unit of E2E execution that the hub builds from one commit and one suite. Each run gets one sealed compose project (fresh volumes, env and credentials newly created inside the run tree, and a port block and network dedicated to the run), and one command runs the pipeline stages: environment creation → build → seal check → startup → suite execution → report. Each host has one active run, and the rest wait in the queue. The scope of zero external communication at runtime is the long-running containers other than the edge, and that is the scope the seal check proves. The edge is a proxy that publishes host ports only on `127.0.0.1`, and its only upstreams are the service names of that project. The hub decides the verdict by reading only the manifest and result JSON that the runner leaves behind. *Words we do not use:* scenario, preset, test job.
- **suite**: The set of flows that a run executes in a single execution, defined in TypeScript inside the consumer repository as a stage → flow → step hierarchy. A stage is the layer that groups flows; a flow is a sequence of steps that achieves one goal, and it declares its id, whether it runs once per environment, and its prerequisite flows. A step is one request, or one wait or capture, and it asserts expectations. When a step fails, its flow stops there, and later flows that depend on that flow are skipped (a skip is not a pass). The runner runs the suite in a container inside the environment, writing the manifest as JSON when it starts and the per-step results as JSON when it ends, and the hub reads only that JSON. *Words we do not use:* scenario, bundle, test suite (the term overlaps with unit tests).
- **kept pool**: The place where the environments of finished runs remain instead of being destroyed automatically. It holds at most five. When a run ends, its containers stop immediately and come back up only when a person resumes them. The only automatic destruction happens when the pool overflows, and it removes the single oldest environment with keep off, other than the run that just finished; every other destruction is done by a person. If all five have keep on, a new run stays in the queue. When the running environments exceed the running cap, kept environments are stopped starting with the one that came up earliest, and a resume brings them back. Destruction also deletes the volumes and leaves only the report bundle and the run metadata. *Words we do not use:* cache, session, sandbox.
- **report bundle**: The set of results a run leaves in the run directory when it ends. It contains the verdict and its reasons, the run metadata, copies of the runner's manifest and results, the list of what was not counted as passed, the frozen signals, and the seal check result. Only files on the allowlist are gathered, and they are redacted with the run redactor; if the rescan just before finalizing catches even one unredacted value, the bundle is discarded and only the caught paths are recorded in the run metadata. It still opens after the environment has been stopped or destroyed. *Words we do not use:* log, artifact.
- **run redactor**: The redaction mechanism built for each run so that one run's credential values do not get out. It redacts text with the list of values read from that run's tree and with patterns that apply even without a value list. The patterns apply from the start, and the value list is reread each time a new credential is created. The live stream, hub responses and the report bundle all pass through redactors built from the same rules and the same source, and no output path bypasses them. The runner redacts first, with its own redactor inside the environment, and it redacts before truncating. *Words we do not use:* filter, log masking.

## Repository conventions

- The repository language is English: code, identifiers, strings, test names, fixtures, documentation, and commit messages.
- `.mise.toml` pins the toolchain (go, bun, goreleaser). `go.mod` declares `go 1.27.0` and `toolchain go1.27.2`. The whole tree uses `CGO_ENABLED=0`; only `go test -race` runs with `CGO_ENABLED=1`, because its race detector requires cgo.
- Generators and checkers are pinned with the `tool` directive in `go.mod`. The contract originates in Go structs; `go generate` produces the JSON Schema (`schema/`) and the type declarations (`sdk/`), and the output is committed. If a diff remains in the generated files, `make verify` fails.
- `make verify` is the only gate. It combines the following into one target: vet; `go test -race`; the generated-files diff; the license gate (`scripts/check-licenses.sh`: no AGPL, no k6 modules); a no-comment check (`scripts/comments_test.go`, run with the tests) that fails on any comment other than `//go:` directives and shebangs; the build; and the binary size measurement. CI (`.github/workflows/verify.yaml`) calls only this target. The sealed-run gate that needs Docker (`make run-env`) runs locally.
- Releases use goreleaser v2. `scripts/build-runners.sh` in `before.hooks` builds the Linux runners first and places them in `internal/runnerbin/bin/`. The gz files are not committed. The release workflow (`.github/workflows/release.yaml`) runs on a `v*` tag in two jobs. `binaries` runs `make verify` and `goreleaser release`, which uploads the archives to GitHub Releases and writes `Casks/cockpit.rb` to `d0lim/homebrew-tap` (secret `HOMEBREW_TAP_TOKEN`, a token that can push to the tap). `npm` runs after it: `scripts/build-npm.sh` assembles `@d0lim/cockpit-sdk` from `sdk/` and `npm/`, and `bun publish` ships it with the tag's version (secret `NPM_TOKEN`). A failed npm job can be rerun alone without re-releasing the binaries. mise installs the same archives through its `github:d0lim/cockpit` backend, so the archive names (`cockpit_<version>_<os>_<arch>.tar.gz`) are part of the install contract. The package holds only the type declarations and the tsconfig base; runtime helpers for scripts (`target`, `expectStatus`, `json`, `poll`) live in the runner's `cockpit:flow` module, never in the package, because the runner bundler refuses bare specifiers.
- Core code does not contain a consumer project's name, service names, DB schemas or topic names. That knowledge lives in the consumer repository's declaration and scripts. Review enforces this; there is no automated check. Tests and testdata use synthetic names; the root `testdata/` copies the shape of real runs with neutral vocabulary.
- Commit messages are `type(scope): English summary`.

## Code discipline

- No file exceeds 300 lines.
- We do not write comments. Invariants move into tests, and decisions move into `docs/`. Identifiers and test names carry the meaning.
- Logging uses only structured logs from `log/slog`. Status is not printed with `fmt.Print*`. The CLI writes user output through return values and an explicitly passed `io.Writer`.
- The plaintext of credentials, tokens, private keys and DB passwords never appears in logs, error messages, responses or file names. Any text that goes out passes through a redactor.
- Code and documentation refer to other code by symbol name, not by line number.
- No site loads consumer repository code into the host process through `require` or `import`. The runner site is a container, and the hub site is a child process.

## Test discipline

- A change that touches a security control (seal assertions, probes, redaction, port boundaries, guards, allowed repositories) puts both the allow and the deny tests in the same commit.
- At every redactor call site, the deny side is proven with an input that carries a planted secret (a fake value like `PLANTED`). One assertion holds both "the plaintext is absent" and "`****` is present". An assertion that checks only the absence of the plaintext passes even when the text is empty.
- A negative assertion ("is rejected", "does not change", "is absent") comes with a positive canary that shows the assertion was actually evaluated. A test that iterates over external commands, a corpus or a set of files also asserts the number of cases it executed. Executing 0 cases is not a pass.
- If a test stays green when its control is removed, the test is decoration. Each security control test file has a mutation record (control · how to disable it · result) at its head, and the result text starts with `red:`. When a mutation survives, we suspect the mutation vector before fixing the test.
- Tests assert what the code returns, stores and sends at its boundary. They do not assert the order of internal calls or the values that fakes return.
- Tests cross-check hand-written tables (assertion lists, rule tables, coverage) in both directions. We do not keep a table that is not cross-checked.
- Test names are English sentences in CamelCase after `Test`. The name says what happens, under which condition.

## Documentation

- `docs/sealing.md` (the five seals and the static assertion table), `docs/lifecycle.md` (the lifecycle transition table) and `docs/verdict.md` (the verdict rules) are the text of the run rules. When code and documentation disagree, we fix the documentation first and then bring the code in line.
- Documentation is written in English. Code identifiers and paths are in backticks.
