# Signals

This page holds the rules of the per-run signal store in `internal/signal`: where signals live, how the frozen segment and the tail work, what is dropped and how readers learn about it. The contract shapes are in `internal/contract/signal.go`.

## Layout

A run's signals live under `runs/<id>/signals/` in the hub state directory.

- `stream.jsonl`: one signal per line, append only. `seq` starts at 1 and increases by one per accepted signal inside the run.
- `segment.json`: whether the stream is frozen, the last frozen `seq`, the next `seq`, the drop counters carried over a compaction, and the read refusal.
- `kv/<collector>.json`: the state of one collector, written atomically and kept across hub restarts. The collector id must match `^[a-z0-9][a-z0-9-]{0,62}$`, and the state is at most 1 MiB. The state port passes each key and value through the run redactor before it is stored, so a credential never reaches the file. For a collector this means: a key or value equal to (or containing) a run credential reads back masked (`****` plus its last four characters), and so does the part of a value that follows a secret-looking name inside it, because the redactor's key-name rules read the value as text: in a stored `{"nextPageToken":"abc"}` or `token=abc`, the `abc` reads back as `****` (names ending in `token`, or `password`, `secret`, `credential`, `session`, `api_key`, `authorization`, `cookie`). The state key is masked on its own, so a secret-looking key name does not hide its value: `set("nextPageToken", cursor)` reads the cursor back unchanged (`TestASecretLookingStateKeyKeepsItsValueButASecretLookingKeyInsideAValueHidesWhatFollowsIt`). Ordinary values round-trip byte-identical, across hub restarts too: hex digests, random ids (base64url included), RFC 3339 timestamps, sequence numbers, UUIDs and JSON objects of them under neutral keys (`TestOrdinaryStateValuesRoundTripByteIdenticalThroughTheHubRedactorAndARestartWhileAPlantedSecretIsMasked`). Inside a stored object, name a pagination cursor `cursor`, not `nextPageToken`.

The memory index is one 8-byte entry per `seq`: the line offset and the quota bucket, or a mark that the record was dropped or superseded. Reopened after 300,000 appends, the index takes 9.2 bytes per record and the heap grows by the same (`BenchmarkIndexMemoryAfterThreeHundredThousandAppends` on an Apple M4 Max). `TestTheReopenedIndexHoldsAtMostSixteenBytesPerRecord` holds a reopened index of 10,000 records to at most 16 bytes per record, for the index and for the heap growth.

## Redaction

Every signal passes the run masker at three points. On append, the string leaves and the map keys are masked, and attributes with credential names are hidden whole (the name check reads the original key). When two keys mask to the same text, both stay: keys the masker leaves unchanged keep their name, and the masked ones follow in the order of their original keys with `#2`, `#3` and so on. On read, and when the frozen segment is copied into the report bundle, every line is masked again with the current value list. A stream opens only with a masker, and an append without one is refused. When the report's rescan discards the bundle, the hub calls `RefuseReads`. The refusal is kept in `segment.json`, so reads of that run stay refused after a restart.

## Frozen segment and tail

When the report is finalized, `Freeze` copies every retained record up to that point into `<bundle>/signals/stream.jsonl`, and those records never change again. Later appends (resume, exec, periodic collection) go to the tail.

| Limit | Default | Applies to | Drop reason |
|---|---|---|---|
| Records per collector | 20000 | before and after the freeze, per window | `collector-quota` |
| Log lines per container | 10000 | before and after the freeze, per window | `container-quota` |
| Records in the tail | 50000 | after the freeze | `tail-cap` |

When a limit is exceeded, the oldest retained record of that bucket (or of the tail) is dropped, never the one just appended, and never a frozen record. The quotas restart at the freeze. Container log lines are events from the hub-owned collector `logs`, with the container name in the attribute `container`, and they count against their container's quota instead of a collector quota. The collector ids `runner`, `logs`, `services`, `supervisor` and `pipeline` are reserved for the hub (`compose.ReservedCollectorIDs`): `runner` writes the runner spans, `logs` the container log lines, `services` the service states, `supervisor` the collector status events, and `pipeline` the stage spans. A consumer collector file with one of these names is refused at submission.

## Reads

A read asks for the signals after a `seq`. The response carries whether the stream is frozen, the last frozen `seq`, and the drop counters by reason. When the next `seq` the reader expects was dropped, the response starts with a resync marker naming the dropped range, then continues with the next retained signals.

An event, metric or span with an `id` that is emitted again from the same collector with the same kind is a revision; a span is a revision only within its own trace, so the same span id in another trace (an exec, for example) is a different span. A metric with an `id` is a series: a collector that re-sends a cumulative total every interval under the same `id` holds one record per series, and the winning record carries the current total. A series that re-sends its total needs no `rev`: a tie goes to the later `seq`, so each new total wins and an unchanged one is not written. Give a series a `rev` only when it keeps rising across hub restarts and resumes (a counter in the collector's state, or a timestamp); a `rev` that starts again from 1 loses to the earlier highest `rev`, and every new total stays superseded until the count passes it. A signal without an `id` is never a revision, so every metric point without one stays its own record. The highest `rev` wins, and a tie goes to the later `seq`. Reads return only the winning revision, and the screen picks winners by the same key. A signal that repeats the current winner (the same body, attributes and span after masking, ignoring `ts`, `tsSource`, `seq` and `rev`) with a `rev` no higher than the winner's is not written: `Append` returns the winner's seq. Collectors and the services observer that re-arm after a hub restart or a resume re-emit their rows from `rev 1`, and an unchanged row keeps its winner, so a winner in the frozen copy stays in the bundle. A higher `rev`, a winner the quota already dropped, or any change in content is written as before; the quota and freeze rules do not change, and a restart replays the same records because nothing was written.

A revision that loses is superseded at once: the earlier winner when a new revision wins, or the new record itself when it arrives with a lower `rev`. A superseded record leaves its quota bucket (and the tail count), so a collector that re-emits the same rows on every tick holds one record per id, not one per tick. It is not data loss: it is not counted in `dropped`, it never starts a resync marker, and the frozen copy holds only the winners at the freeze. A frozen record is never superseded away. When a later revision of a frozen winner arrives, the frozen record stays in the stream file and the frozen copy, and reads return the new winner.

## Metric bodies

A metric carries a `name` and a numeric `value`, and may carry a `unit` (free text such as `ms` or `By`), a `type` (`gauge`, `sum`, `histogram` or `summary`) and a `histogram`. A histogram body holds the number of observations `count`, their `sum`, the ascending bucket upper bounds `bounds` and the observations per bucket `counts`; `counts` has one entry more than `bounds`, because the last bucket holds everything above the last bound, or both are empty. A metric has a `histogram` exactly when its `type` is `histogram`, and then its `value` equals the histogram's `sum`. `Append` refuses a metric that breaks these rules. The signal port keeps the collectors written before these fields existed working: it keeps `unit`, `type` and `histogram` together only when all three are well formed and the body they make passes these rules, and otherwise it stores the metric with its `name` and `value` alone, as if none of the three had been sent. A Prometheus-style `"type":"counter"` or `"untyped"`, a `unit` that is not a string, a `histogram` type without a histogram, or a histogram whose `value` is not its `sum` therefore stores a metric without a unit, type or histogram instead of being refused. A collector that wants its unit kept sends a valid `type` (or none) next to it (`TestCollectorMetricFieldsThatDoNotFormAValidSetAreDroppedAndTheNameAndValueAreStored`).

## Restart and compaction

On start, the index is rebuilt from `stream.jsonl`. An incomplete last line is cut off. A corrupt line before the last one fails the open instead of dropping data. The quotas and the tail cap are replayed in `seq` order, so the same records count as dropped as before the restart.

When more dropped or superseded records have accumulated since the last rewrite than there are retained records (and at least 4096), the file is rewritten with only the retained records. Each run of consecutive superseded `seq`s is kept as one tombstone line `{"superseded":[from,to]}`, so a restart marks them superseded again instead of reading them as a gap. The drop counters move into `segment.json`, and `seq` keeps increasing from where it was. Replay applies the revision rule in `seq` order, so a restart supersedes the same records as before.

## Stage spans

The hub records when each pipeline stage started and ended in the run record, as `stages` in the run's `meta.json`: a list of `store.StageTime` entries `{stage, start, end, outcome}`, where `stage` is the phase the stage runs in. The record is written on every change, so a hub restart keeps the times. `Hub.Pipeline` writes the start when it picks a stage, and the end with the outcome in the same write as the event that closes the stage: `ok` for the stage's own event, `error` for a failure and `incomplete` for an abort. The hub never resumes a pipeline after a restart. Reconciliation closes the run instead, and it ends the open entry with `error` in the same write as its `observed` event, before any report.

From these entries the hub writes spans into the run trace (the trace id is the run id) with the collector `pipeline` and the time source `host`. The root span `pipeline` gets one child `stage:<name>` per ended entry, named `<name>`, with the entry's start, end and outcome as its status. The names are `prepare`, `build`, `seal`, `boot`, `suite` and `report`. The root starts with the first stage, ends with the last ended one, and takes the worst status of its stages (`error` over `incomplete` over `ok`). A stage span carries the attributes `stage` and `status`. The runner's `run` span has `stage:suite` as its parent, so the run trace reads `pipeline` → `stage:<name>` → `run` → `flow:<flow>` → `step:<flow>/<step>` → `call:<flow>/<step>/<n>`.

- The report appends the stage spans before the runner spans (`DefaultReport`), so every parent has a lower `seq` than its children. The report stage is still open at that point, so the frozen copy holds the stages from `prepare` to `suite`.
- When the run ends, the pipeline appends the stage spans again from the record. A span that repeats its winner is not written (see Reads), so for a reported run this adds only `stage:report` and a revision of `pipeline` that ends with it, both in the tail. A kept run reads six stage spans live, and a destroyed run reads five from its bundle. A run that ends before its report gets all of its stage spans at this point.
- A run that the hub reports after a restart gets the stage spans of the entries that ended before the restart, the interrupted one included with status `error`, and no `stage:report`. A run that the hub closes after a restart without a report gets no stage spans, and neither does an entry that the pipeline could not close because another event moved the run first. A resume or an exec adds no stage spans.

## Runner spans

The run, flow and step spans come from the runner's result file, never from scripts. The run trace id is the run id, and the span ids are `run`, `flow:<flow>` and `step:<flow>/<step>`. The `run` span's parent is `stage:suite` (see Stage spans). A step that was still running when the runner stopped ends at the container exit time with status `incomplete`, and so do its flow and the run span. An exec is a new trace `<run id>/exec/<name>` whose root span `exec` has no parent and links to the run span. The report stage appends the run trace from a schemaVersion 2 result to the run's stream before the freeze, so the frozen copy holds it; each `cockpit runs exec` appends its trace to the same stream after the exec, with `<name>` the exec result file name without `.json`. A step span carries the attributes `flow`, `step` and `status`, plus one attribute `ref.<name>` per ref the step recorded (`docs/guide.md`); a name the step recorded more than once gets `ref.<name>.2`, `ref.<name>.3` and so on for the later values. Each request the step recorded becomes a span `call:<flow>/<step>/<n>` (counting from 1) under the step span, named `<METHOD> <path>`, with the attributes `method`, `host`, `path` and `status` (absent when the request failed before a response) and the status `ok` for a response below 400, `error` otherwise. A request with no duration ends at its start. The container exit time is when the hub saw the runner container end (its `docker wait` returned, or the limit or an abort stopped it); a run the hub reports after a restart never saw that exit and uses the report time. A span the stream refuses is listed in the bundle as unread under `spans`.

## Correlation keys

An attribute whose key starts with `ref.` is a correlation key: the part after the prefix names what the value identifies (`ref.transaction`), and the value is the id. Two signals that carry the same value under any `ref.` key are about the same thing, whichever collector wrote them. The runner's step spans carry the refs a flow recorded, and a collector adds `ref.` attributes to the rows, notifications or log lines it emits. Keys and values pass the run masker like every other attribute, so a value the hub treats as a credential reads back masked and links nothing.

## Reads after destroy

When a run is destroyed its live stream is removed, and a read falls back to the frozen copy in the report bundle (`<bundle>/signals/stream.jsonl`), masked again on the way out. The response says `source: bundle`; a read of the live stream says `source: live`. A run without a bundle answers not found as before.
